## Goal
DjangoのAPITestCase（テストクライアント）に依存しない、実際のHTTPサーバーに対するE2Eテストを追加し、CRUD全フローのHTTP契約をlive_server上で検証する。

## Scope
- In scope: pytest-django導入、live_serverベースのE2Eテスト、CRUD全フローのHTTP契約検証
- Out of scope: Company APIのE2Eテスト、認証・認可、パフォーマンステスト、負荷テスト、並行リクエスト競合検証（別計画）、PATCHトランザクションロック実装（別計画）

## Important requirements
- 既存のDjangoテスト（APITestCase）と併存できること。
- E2Eテストは実際のHTTP接続（localhost:port）を使用する。
- Category作成には既存Companyが必要。E2Eセットアップに限り、Django ORMでCompanyを事前作成することを許可する。
- テスト実行前にDBマイグレーションが自動適用されること。
- テストは決定的であり、CI上で安定して通過すること。

## Transitions
- N/A。HTTP APIのみの追加・改善。

## Change targets
- `pyproject.toml` - `dependency-groups.dev` へ pytest-django, httpx を追加
- `pyproject.toml` - `[tool.pytest.ini_options]` にpytest設定を追加
- `uv.lock` - ロックファイル更新
- `api/tests/e2e/` - E2Eテストディレクトリ
  - `conftest.py` - 共通フィクスチャ（live_server, httpxクライアント, Company fixture）
  - `test_category_crud.py` - CRUD全フロー

## Tasks
1. pytest-djangoとhttpxを導入する
- Deliverables: pyproject.tomlへのdev依存追加、pytest設定
- Tests: なし（導入のみ）

2. E2Eテスト基盤（conftest）を構築する
- Deliverables: live_serverフィクスチャ、httpxクライアントフィクスチャ、Companyの事前作成（ORM fixture）、テスト後のクリーンアップ
- Tests: 接続確認のダミーテスト

3. CRUD全フローのE2Eテストを追加する
- Deliverables: 一覧→作成→詳細→更新→部分更新→削除のシーケンシャルテスト、入力検証、参照整合性
- Tests: `test_category_crud.py` の全テストがlive_serverで通過すること
- 検証対象:
  - レスポンス項目: `id`, `company_id`, `name`, `parent_category_id`, `created_at`, `updated_at`
  - 作成後の永続化: 作成直後に詳細取得で同一データが返ること
  - 削除後の404: 削除後に詳細取得で404が返ること
  - 入力検証: 必須項目不足、不正UUID、255文字超の名前、`company_id: null`
  - 参照整合性: 存在しないCompany、存在しない親Category
  - PATCHの明示的null: `name`/`company_id` にnullを指定すると400

4. 全体検証を行う
- Deliverables: 既存テスト全件とE2Eテストの併存確認、pyright通過
- Tests: `uv run python manage.py test` と `uv run pytest api/tests/e2e/` の両方が通過すること

## 要件と自動テストの対応
- 一覧取得がlive_serverで200を返す -> `test_list`
- 作成がlive_serverで201を返し、全フィールドが含まれる -> `test_create`
- 作成直後に詳細取得で同一データが返る -> `test_retrieve_after_create`
- PUT更新がlive_serverで200を返し、全フィールドが含まれる -> `test_update`
- PATCH部分更新がlive_serverで200を返し、更新後永続化が確認できる -> `test_partial_update`
- 削除がlive_serverで204を返し、その後404になる -> `test_destroy`
- 存在しないリソースが404を返す -> `test_missing_returns_404`
- 必須項目不足で400 -> `test_create_missing_name`
- 不正UUIDで400 -> `test_create_invalid_uuid`
- 255文字超の名前で400 -> `test_create_name_too_long`
- `company_id: null`で400 -> `test_create_null_company_id`
- 存在しないCompanyで400 -> `test_create_missing_company`
- 存在しない親Categoryで400 -> `test_create_missing_parent`
- PATCHの明示的nullで400（name） -> `test_patch_null_name`
- PATCHの明示的nullで400（company_id） -> `test_patch_null_company_id`
- 既存テストとE2Eテストが併存する -> 両方のテストスイートが独立して通過すること
- 空のテストDBからマイグレーション適用後に成功する -> `conftest.py` のlive_server起動

## Acceptance criteria
- `uv run pytest api/tests/e2e/` がスキップなしで成功する。
- 既存の `uv run python manage.py test` がE2E追加後も全件成功する。
- E2Eテストがdeterministic（決定的）であり、複数回実行しても同じ結果になる。
- 作成・更新後のレスポンスに `id`, `company_id`, `name`, `parent_category_id`, `created_at`, `updated_at` が含まれる。
- 削除後に詳細取得で404が返る。
- 不正入力に対して400が返り、エラーレスポンスに検証メッセージが含まれる。
- `uv run --with pyright pyright` が0エラーで終了する。

## Notes
- pytest-djangoの `live_server` フィクスチャを使用し、実際のWSGIサーバーを起動する。
- httpxをHTTPクライアントとして使用（同期APIで十分）。
- 既存のDjangoテストランナー（unittestベース）とpytestは別々に実行する。
- E2Eテスト本体はHTTP APIのみを通じて検証する。Companyの事前作成はセットアップに限りORMを使用する。
- 並行リクエスト競合検証とPATCHトランザクションロックは別計画として扱う。
